## 0. Кто ты и жёсткие правила

Ты — **исполнитель-наполнитель базы данных смартфонов**. Твоя работа — найти в открытых источниках и записать
проверяемые факты о смартфонах в JSON-файлы строго по схеме из этого ТЗ. Ты не программист этого проекта: код,
схему и формулы не меняешь.

Правила обязательны. Нарушение любого делает пачку непринятой.

1. **Ничего не выдумывай.** Каждое число и каждый факт берётся из источника. Источника нет — ставь `null` и
   `"_q": "unknown"`. Правдоподобная выдумка хуже пустого поля: по этим данным обучается нейросеть.
2. **У каждого блока есть достоверность `_q`:**
   - `verified` — прямо указано в источнике (сайт производителя, замер лаборатории, карточка магазина);
   - `estimated` — вывод из косвенных данных (сестринская модель, пересчёт, рубрика по обзорам);
   - `user_hypothesis` — утверждение пользователя, которое ещё не проверено;
   - `random` — демо-число из рандом-версии; **ты должен заменить все `random`**;
   - `unknown` — искал, не нашёл.
3. **У каждого блока есть источники `_src`** — массив id из справочника `sources.json` (приложение G). Через
   двоеточие уточняется страница: `"gsmarena:samsung_galaxy_s25_ultra-13322"`, `"dxomark:Samsung/Galaxy-S25-Ultra"`.
   **Для `_q: "verified"` ссылка на конкретную страницу обязательна** (правило H3): голое `"gsmarena"` — это не проверка.
4. **Схему не меняй.** Никаких новых полей, переименований, вложенных объектов «от себя». В схеме стоит
   `additionalProperties: false` — лишнее поле валит сборку. Нужно новое поле — опиши это в отчёте пачки
   (раздел 13), но в файлы не добавляй.
5. **Единицы фиксированы:** дюймы, Гц, мА·ч, Вт, граммы, мм, рубли (целые), доллары США (целые), ГБ.
   **1 ТБ = 1024 ГБ.** Даты — ISO: `2026-11-20` или `2026-11` (только для `release_date`).
6. **Типы строгие:** числа — числами (`5500`, а не `"5500"` или `"5 500 мА·ч"`), логические — `true/false`,
   пустое — `null`. Комментарии внутри JSON запрещены: JSON их не поддерживает.
7. **Вычисляемые поля не заполняй** — их считает скрипт сборки (раздел 7): площадь сенсора, оценка «железа»
   модуля, итоговая оценка модуля, сводка камер, кратность зума (если известно фокусное), процентили DXOMARK.
8. **Не переносить «приколы» на весь бренд.** «Pixel греются» — это гипотеза, которую проверяют для **каждой**
   модели отдельно. То же для серий: «у POCO X8 Pro желтит экран» не означает, что желтит у POCO X8 Pro Max.
9. **Отрицательный «прикол»** записывается только при наличии замера лаборатории ИЛИ минимум двух независимых
   источников. Ссылки кладутся в `evidence`. Иначе не записывай.
10. **Фото** — только с понятной лицензией и автором (раздел 10). Не бери картинки GSMArena и фото продавцов
    с маркетплейсов.
11. **Существующие slug не переименовывай.** 282 модели уже есть в базе (раздел 4.3) — к ним привязаны обученная
    модель, история цен и фото.
12. **Регион и версия модели — разные модели,** если отличаются характеристики: Exynos и Snapdragon, 4G и 5G,
    китайская и глобальная версия с другим чипом или батареей. Разные модели = разные файлы.
13. **Работай пачками** по одному бренду, не больше 20 моделей за пачку, в формате раздела 13.
14. **Перед сдачей каждой пачки** пройди чек-лист раздела 15 и честно перечисли, чего не нашёл.
15. **Не обходи защиты сайтов:** капчи, пейволлы, запреты для ботов. Сайт закрыт — бери следующий источник
    из таблицы раздела 10.
16. **Честно о своих возможностях.** Первой строкой отчёта каждой пачки напиши: есть ли у тебя сейчас доступ к
    интернету и до какой даты у тебя есть сведения. Нет доступа к источникам — ничего не помечай `verified`.
    Модели и события после даты твоих знаний не заполняй по памяти: пропусти их и перечисли в отчёте.

## 0.1. Запрещено — скрипт сборки проверяет это автоматически

**«Заменить `random`» значит найти настоящее значение и записать его вместе со ссылкой на страницу.** Сменить
только пометку `_q` у старого числа — подлог, даже если число «похоже на правду». Не нашёл настоящее значение —
оставь блок как есть с `"_q": "random"` и перечисли его в отчёте пачки. Частично заполненная честная база
принимается, «проверенная» выдумка — нет.

Скрипт `python tools/build_catalog.py --check` ловит нарушения по правилам ниже; хотя бы одно нарушение — пачка
не принимается.

| Правило | Что запрещено | Как правильно |
|---|---|---|
| H1 | `processing_basis: "random"` при `_q` не `random` | Оценил модуль по рубрике 7.3 — `processing_basis: "reviews_rubric"` и новое число; не оценил — оставь `random` |
| H2 | Текст «Демо…» в `note_ru`, источник `random` в `_src` или `price_src` при `_q` не `random` | Демо-«прикол», который не подтвердился, **удали**. Демо-цену замени ценой из магазина с датой |
| H3 | `_q: "verified"` без ссылки на конкретную страницу (`id:страница`) — в файлах моделей и в справочниках | `"_src": ["gsmarena:xiaomi_15_ultra-13657", "manufacturer:mi.com/global/product/xiaomi-15-ultra/specs"]` |
| H4 | «Прикол» с `_q: "verified"` и пустым `evidence` | Прямые ссылки на замер или обзоры в `evidence` |
| H5 | `quirks_checked: true`, если остались «приколы» не `verified` или без ссылок | Неподтверждённые «приколы» удали, затем ставь `quirks_checked: true` |
| H6 | Слово «проверено» в `note_ru` без ссылок | Пиши, что именно измерено, и давай ссылку |
| H7 | Мегапиксели модуля расходятся с сенсором из справочника больше чем на 15% (сенсор угадан) | Сенсор прямо назван в источнике — ставь его; иначе `"sensor": null` |
| H8 | `slug` или `full_name` не по правилу раздела 4.2 | Строй их ровно по алгоритму 4.2 |
| H9 | Дубль существующей модели под другим slug (`samsung-galaxy-z-flip-6` при `samsung-galaxy-z-flip6`; `cmf-phone-2-pro` при `nothing-cmf-phone-2-pro`) | Перед созданием файла поищи модель среди существующих; нашёл — правь существующий файл |
| H10 | `msrp_usd`, пересчитанный из рублёвой цены по курсу | Только официальная стартовая цена производителя в долларах; нет её — `null` |
| H11 | Даты выхода-заглушки (`2024-06-01` у многих моделей) | Точная дата из источника, либо месяц (`2024-06`), либо `null` |
| R1 | Справочники не по `refs.schema.json`: нет `antutu_k`, `_src`; лишние поля `antutu_v10`, `cores`, `gpu`, `geekbench6_sc` | Ровно поля схемы: `antutu_k` в тысячах (целое), `geekbench_sc`/`geekbench_mc`, у сенсоров `_src` обязателен |

Готовность всей работы проверяется командой `python tools/build_catalog.py --check --final` (критерии раздела 16).

## 1. Контекст проекта

- **Что это.** Приложение подбирает смартфон по анкете пользователя с помощью машинного обучения: метки классов,
  кластеризация KMeans, нейросеть MLP, регрессия «справедливой цены». Есть настольная версия на Python
  (PySide6) и быстрый веб-сервер на Rust (axum) — он считает подбор за десятки микросекунд.
- **Как сейчас устроены данные.** `data/phones_seed.csv` (286 строк, одна строка = модель с ОДНОЙ конфигурацией
  памяти) → SQLite `phones.db` → Python обучает модели → `rust_backend/model.json` → Rust-сервер и сайт.
- **Чего не хватает:**
  - конфигураций памяти: у модели одна пара ОЗУ/ПЗУ и одна цена, а фильтра по ОЗУ нет вовсе;
  - камер: одно число `camera_mp` вместо модулей, сенсоров, зума, макро и качества обработки;
  - фото: есть только у 41 модели из 286;
  - особенностей моделей («приколов») и категории «Смартфоны с интересными возможностями»;
  - объёма: нужно около 1000 моделей вместо 286.
- **Что уже сделано.** В ветке `random-future` («рандом цифры по камерам и всему-всему-всему на будущее»)
  собран каркас новой БД по этому ТЗ: 285 файлов моделей, справочники, сборка SQLite, сайт показывает новые данные.
  Реальные поля перенесены из старой базы, а всё новое (камеры, обработка, доп. конфигурации, «приколы»,
  заглушки фото) — **случайные числа** с `"_q": "random"`. Твоя задача — заменить их настоящими данными и
  расширить базу до ~1000 моделей.
- **Что будет потом (не твоя задача).** На полной БД переобучат нейросеть и переделают подбор (раздел 17).

## 2. Цели

| № | Цель | Что значит «готово» |
|---|---|---|
| 1 | Фото каждого смартфона, листалка на сайте | ≥ 3 настоящих фото у ≥ 90% моделей, ≥ 1 у 100%; у каждого фото лицензия и автор |
| 2 | Расширить базу | ≈ 1000 моделей (не меньше 950), 2022–2026, все бренды, продающиеся в РФ, + примечательные модели не для РФ |
| 3 | Настройка по ОЗУ, все конфигурации памяти | У каждой модели ВСЕ официальные пары ОЗУ/ПЗУ, у каждой — цена в РФ с датой (или `null` + MSRP) |
| 4 | Модули камер и справочник сенсоров | Каждый модуль отдельно: роль, сенсор, МП, диафрагма, ЭФР, OIS, автофокус; сенсоры — в справочнике |
| 5 | Макро, аппаратный и цифровой зум | `macro_mode`, кратность каждого телевика, lossless-зум, максимальный цифровой зум |
| 6 | Качество обработки каждой системы на каждом телефоне | `processing_score` 0–100 по рубрике раздела 7 для КАЖДОГО модуля (кроме depth) |
| 7 | «Приколы» каждой модели | ≥ 1 подтверждённая особенность у ≥ 80% моделей; у 100% `quirks_checked: true` |
| 8 | Смартфоны с интересными возможностями | Все модели категорий раздела 9 есть в базе и отмечены |

## 3. Архитектура хранения (согласована, не менять)

```
data/catalog/**.json         ← ЭТО ЗАПОЛНЯЕШЬ ТЫ (источник правды)
        │
        │  python tools/build_catalog.py   — проверка по схеме, ссылочная целостность, формулы раздела 7
        ▼
data/catalog.db  (SQLite, схема v2)  ──копия──►  rust_backend/catalog.db
        │                                              │
        │ представление v_ml_phones                    │ Rust (rusqlite) читает при старте в память:
        ▼                                              ▼ компактные типы, мгновенные фильтры
Python ML (переобучение — позже)               веб-сервер и сайт
```

Принципы:

- **Один JSON-файл на модель** + JSON-справочники. Модели добавляют по одной, изменения видны построчно
  в git, нейросети и люди работают параллельно без конфликтов.
- **Стабильный ключ `slug`** вместо автоинкремента: фото, цены и отзывы не «съезжают» при пересборке.
- **БД пересобирается целиком** из файлов и руками не правится. Версия схемы хранится в `meta.schema_version`;
  меняют её только разработчики (новый `catalog_v3.sql` + миграция).
- **Провенанс у каждого блока** (`_q`, `_src`): база может быть частично настоящей и частично демо, а сайт честно
  показывает, что проверено.
- **Справочники вместо повторов:** сенсор Sony LYT-900 описан один раз, телефоны ссылаются на него по slug.
- **История цен отдельно** (`price_history.csv`), по конкретной конфигурации, хранятся только изменения цены.

## 4. Файлы и именование

### 4.1. Раскладка `data/catalog/`

```
data/catalog/
  dataset.json                  название и версия набора (не трогать)
  schema/phone.schema.json      JSON Schema файла модели          — приложение A
  schema/refs.schema.json       JSON Schema справочников          — приложение B
  schema/catalog_v2.sql         структура SQLite                  — приложение C
  schema/example.*.json         пример заполненного файла         — приложение D
  brands.json                   бренды
  chipsets.json                 чипы (AnTuTu, Geekbench, техпроцесс)
  sensors.json                  сенсоры камер
  quirk_types.json              типы «приколов»                   — приложение E
  special_categories.json       категории интересных возможностей — приложение F
  sources.json                  справочник источников             — приложение G
  price_history.csv             история цен: slug,ram_gb,rom_gb,date,source,price_rub
  phones/<бренд>/<slug>.json    файл модели
```

### 4.2. Как строить slug (точно так же считает код на Python и Rust)

1. `full_name` = бренд + пробел + модель, но **если модель уже начинается с названия бренда — бренд не повторять**
   (`POCO` + `POCO F7` → `POCO F7`; `Xiaomi` + `Redmi Note 14` → `Xiaomi Redmi Note 14`).
2. Заменить каждый `+` на ` plus `.
3. Нижний регистр; каждую последовательность символов вне `a-z0-9` заменить одним `-`; обрезать `-` по краям.

| Бренд + модель | slug |
|---|---|
| Samsung + Galaxy S25+ | `samsung-galaxy-s25-plus` |
| Samsung + Galaxy S25 Ultra | `samsung-galaxy-s25-ultra` |
| POCO + POCO X8 Pro Max | `poco-x8-pro-max` |
| Xiaomi + Redmi Note 14 Pro+ 5G | `xiaomi-redmi-note-14-pro-plus-5g` |
| Apple + iPhone 17 Pro | `apple-iphone-17-pro` |
| Nothing + Phone (3a) Pro | `nothing-phone-3a-pro` |
| realme + realme GT 7 | `realme-gt-7` |

Конфигурация памяти **не входит** в slug: «iPhone 17 Pro 512GB» — это конфигурация модели `apple-iphone-17-pro`,
а не отдельная модель.

### 4.3. Бренды и папки

- Папка = slug бренда. Суббренды — отдельные бренды с `parent`: `poco` (parent `xiaomi`), `redmagic`
  (parent `nubia`), `iqoo` (parent `vivo`).
- Redmi остаётся внутри бренда `xiaomi` (модель «Redmi 15» → `xiaomi-redmi-15`), CMF — внутри `nothing`
  («CMF Phone 2 Pro» → `nothing-cmf-phone-2-pro`). Так уже устроена база, и менять это нельзя.
- **Существующие модели:** в ветке `random-future` лежат 285 файлов, из них 282 участвуют в подборе. Их slug,
  имена файлов, `brand`, `name`, `full_name` и `in_ml` **не меняются** — ты заменяешь только `random` на настоящие
  данные и проверяешь `estimated`.

## 5. Формат файла модели

Полная схема — в приложении A, заполненный пример — в приложении D. Ниже — смысл каждого поля.

### 5.1. Верхний уровень

| Поле | Тип | Правило |
|---|---|---|
| `slug` | строка | по разделу 4.2; совпадает с именем файла |
| `brand` | строка | slug бренда из `brands.json`; совпадает с папкой |
| `name` | строка | модель без бренда, как в маркетинге: «Galaxy S25 Ultra» |
| `full_name` | строка | по разделу 4.2, шаг 1 |
| `aliases` | массив строк | другие написания для сопоставления цен из магазинов («Galaxy S25U»). НЕ названия других моделей |
| `os` | `Android` / `iOS` / `HarmonyOS` | система из коробки |
| `release_date` | `ГГГГ-ММ-ДД` / `ГГГГ-ММ` / `null` | дата начала продаж (не анонса) |
| `year` | целое | год начала продаж |
| `status` | `on_sale` / `discontinued` / `announced` / `china_only` | `china_only` — продаётся только в Китае |
| `availability_ru` | `official` / `parallel_import` / `not_sold` | как модель попадает в РФ; `not_sold` — нет в крупных магазинах РФ |
| `form_factor` | `bar` / `book_fold` / `flip` / `trifold` / `rugged` / `other` | `rugged` — защищённый корпус (IP68+IP69+MIL или ≥ 300 г) |
| `in_ml` | логическое | `true` — участвует в подборе. **Новые модели: `true`, если `availability_ru` ≠ `not_sold` и есть цена; иначе `false`** |
| `chipset` | slug / `null` | из `chipsets.json` |

### 5.2. `specs` — характеристики

Диагональ основного экрана (у складных — внутреннего), `cover_screen_in` — внешний экран складного, частота
экрана, тип и пиковая яркость, батарея, проводная и беспроводная зарядка, вес, толщина, IP, флаги 5G/NFC/eSIM/ИК,
3,5 мм, карта памяти, годы обновлений по официальной политике. Один `_q` и `_src` на весь блок: если часть полей
взята из другого источника, перечисли все источники.

### 5.3. `variants` — конфигурации памяти и цены

- **Все официальные** пары ОЗУ/ПЗУ, которые продавались в мире, даже если в РФ есть не все.
- Ровно одна `is_base: true` — самая массовая конфигурация в РФ (обычно самая дешёвая из продающихся).
- `ram_gb` — **физическая** ОЗУ («12 ГБ + 12 ГБ расширения» → 12).
- `price_rub` — минимальная цена нового телефона у крупных продавцов РФ (Яндекс Маркет, DNS, М.Видео, Ситилинк,
  Ozon, Wildberries, официальный магазин) на дату `price_date`; `price_src` — где взята. Б/у, восстановленные,
  «под заказ из Китая» с ожиданием > 14 дней — не считаются. Нет в продаже в РФ — `price_rub: null`.
- `msrp_usd` — официальная стартовая цена в США или мире, если её объявляли.

### 5.4. `cameras` — каждый модуль отдельно

| Поле | Правило |
|---|---|
| `role` | `main` основная · `ultrawide` сверхширик · `tele` телевик без перископа · `periscope` перископ · `macro` отдельный макро-модуль · `depth` датчик глубины · `mono` монохромный · `front` фронтальная · `front_ultrawide` вторая фронтальная · `cover` камера внешнего экрана складного |
| `position` | порядок внутри роли: 0, 1… (например, два телевика — `tele` 0 и `tele` 1) |
| `sensor` | slug из `sensors.json`; точное название сенсора неизвестно — `null` (НЕ угадывать по мегапикселям) |
| `mp` | мегапиксели модуля |
| `aperture` | число f: 1.8 для f/1.8 |
| `focal_mm` | **эквивалентное** (35 мм) фокусное расстояние |
| `fov_deg` | угол обзора по диагонали, если указан |
| `optical_zoom_x` | заявленная кратность относительно основной (0.6, 3, 5); если известно `focal_mm`, скрипт пересчитает сам |
| `ois` | оптическая стабилизация модуля |
| `af` | `none` / `fixed` (фикс-фокус) / `contrast` / `pdaf` / `dual_pixel` / `laser` |
| `min_focus_cm` | минимальная дистанция фокусировки (важно для макро) |
| `video_max` | лучший режим видео модуля: `4K60`, `8K30`… |
| `processing_score` | качество обработки этого модуля на этом телефоне, 0–100, по рубрике 7.3. Для `depth` — `null` |
| `processing_basis` | `reviews_rubric` — по обзорам; `dxomark` — если основой были подоценки DXOMARK |

### 5.5. `camera_features`

`macro_mode`:
- `dedicated` — отдельный макро-модуль;
- `ultrawide_af` — сверхширик с автофокусом снимает макро;
- `tele_macro` — телевик фокусируется близко;
- `none` — макро нет.

Остальные поля:
- `macro_min_focus_cm`;
- `lossless_zoom_x` — заявленный «оптического качества» зум кропом с сенсора;
- `max_digital_zoom_x` — максимальный цифровой зум из спецификации;
- `dxomark` — подоценки DXOMARK с указанием версии протокола и ссылкой, или `null`, если теста нет.

### 5.6. `quirks`, `quirks_checked`, `special`, `photos`

- `quirks` — особенности по разделу 8; `quirks_checked: true` ставится, когда обязательные источники раздела 10
  проверены, даже если особенностей не нашлось.
- `special` — категории раздела 9.
- `photos` — по разделу 10, в порядке показа: спереди → сзади → сбоку/под углом → другие цвета.

### 5.7. Справочники

- **`sensors.json`** — каждая запись описывает один сенсор:
  - `slug` (`sony-lyt-900`) и `name` (`Sony LYT-900`);
  - `vendor`, `mp`;
  - `size_inch` — оптический формат строкой (`"1"`, `"1/1.3"`);
  - `diag_mm` — если производитель даёт реальную диагональ;
  - `pixel_um`, `tech` (`stacked`, `dcg`, `lofic`, `quad_bayer`…).

  Источник — страницы производителя сенсора.
- **`chipsets.json`** — `slug`, `name`, `vendor`, техпроцесс, AnTuTu (тысячи, **версию теста укажи в `_src`**),
  Geekbench одноядерный и многоядерный, год.
- **`brands.json`** — `slug`, `name` (как пишет производитель), `parent`, страна.
- **`price_history.csv`** — дописывай строки `slug,ram_gb,rom_gb,date,source,price_rub`, когда находишь цену
  с датой. Скрипт оставит только изменения цены.

## 7. Формулы и оценки (считает скрипт — ты заполняешь только сырые данные и `processing_score`)

### 7.1. Сенсор

- Диагональ: `diag_mm` из справочника, иначе `16 / знаменатель формата` (формат 1/1.3″ → 12,3 мм; 1″ → 16 мм).
- Площадь кадра 4:3: `area = 0,48 · diag²`.
- Оценка сенсора:
  `hw_score = clip(100 · (ln area − ln 3) / (ln 125 − ln 3) + бонус, 0, 100)`,
  бонус: LOFIC +4, DCG +2, stacked +2.

### 7.2. «Железо» модуля

- «Светосила»: `light = area / f²`.
- `module_hw = clip(100 · (ln light − ln L₀) / (ln L₁ − ln L₀) + 5·OIS + 3·(автофокус pdaf/dual_pixel/laser), 0, 100)`.
- Границы `L₀ … L₁` по ролям:

  | Роль | L₀ … L₁ |
  |---|---|
  | `main` | 1,5 … 50 |
  | `ultrawide`, `tele`, `periscope`, `mono` | 1 … 15 |
  | `front`, `front_ultrawide`, `cover` | 0,8 … 8 |
  | `macro` | 0,5 … 5 |

- `depth` не оценивается. Нет сенсора или диафрагмы — оценки «железа» нет.
- Оптическая кратность модуля: `focal_mm / focal_mm основной`, округление до 0,1.

### 7.3. Обработка — ЭТО ЗАПОЛНЯЕШЬ ТЫ (`processing_score`, 0–100)

Шкала **абсолютная на 2026 год**: старые модели честно получают меньше. Оценивай конкретный модуль конкретного
телефона по обзорам этого телефона. Не по бренду и не по сенсору: одинаковый сенсор у разных брендов снимает
по-разному, именно это поле и ловит разницу.

| Балл | Уровень | Признаки |
|---|---|---|
| 90–100 | лидер рынка | топ-10 DXOMARK своего года по этому модулю; обзоры называют лучшим в классе; нет заметных проблем ни днём, ни ночью |
| 75–89 | хороший флагман | днём отлично, ночью хорошо; мелкие замечания (лёгкий перешарп, небольшие задержки) |
| 60–74 | средний класс | днём хорошо, ночью шумы и «мыло»; ограниченный динамический диапазон |
| 40–59 | бюджетный уровень | заметные шумы, «акварель», проблемы с HDR и балансом белого, задержка затвора |
| 0–39 | слабый | серьёзные проблемы даже днём; модуль «для галочки» |

Что смотреть по ролям:
- **основная** — динамический диапазон, ночь, детализация, цвет и кожа, задержка затвора;
- **сверхширик** — резкость по краям, дисторсия, совпадение цвета с основной;
- **телевик и перископ** — детализация на родной кратности и на промежуточных (2×, 5×, 10×), ночь;
- **фронтальная** — кожа, HDR, фокус;
- **макро** — детализация и удобство.

Нет обзора, который упоминает модуль, — бери сестринскую модель того же бренда и года с тем же модулем:
`"_q": "estimated"`, в `_src` пиши `"estimated:sibling:<slug>"`.

**Поправка по DXOMARK (считает скрипт).** Если у модели есть подоценка DXOMARK для роли (Photo → основная,
Zoom Wide → сверхширик, Zoom Tele → телевик/перископ, Selfie → фронтальная), скрипт считает
`processing_dxo = clip(50 + (процентиль подоценки в базе − module_hw))`. Итоговая обработка —
среднее твоей рубрики и `processing_dxo`. Тебе нужно только аккуратно записать подоценки в `camera_features.dxomark`
и указать версию протокола: оценки v5 и v6 напрямую не сравнимы.

### 7.4. Итоги

- Итог модуля: `total = round(0,5 · module_hw + 0,5 · processing)`.
- Сводка камер (`camera_summary`):
  - `rear_count` — задние модули без `depth`;
  - `max_optical_zoom_x` — максимум по телевикам, 1,0 если их нет;
  - `main_score`, `ultrawide_score`, `tele_score` (лучший телевик/перископ), `front_score`;
  - `macro_score`: отдельный модуль → его итог; `ultrawide_af` → 0,9 × итог ширика; `tele_macro` → итог телевика; `none` → 0;
  - `overall_score = 0,5·main + 0,2·ultrawide + 0,2·tele + 0,1·front` (отсутствующий модуль = 0).

**Тяжесть (`severity`):** 1 — мелочь или проявляется редко; 2 — заметно многим пользователям; 3 — серьёзно мешает
каждый день или массовый дефект. Для положительных «приколов» это сила плюса: 3 — выдающаяся черта.

**Как записывать:**
- `note_ru` — одно-два предложения по делу, с цифрой, если она есть: «ШИМ 240 Гц на яркости ниже 40%».
- `evidence` — прямые ссылки на замер, обзор или ветку владельцев. Для отрицательных — минимум 2 ссылки или 1 замер.
- `_q: "verified"` только если правило из `measure_rule` выполнено.
- Проблема исправлена обновлением — severity 1 и версия прошивки в `note_ru`.

**Гипотезы пользователя — проверить первыми:**

| Гипотеза | Что сделать |
|---|---|
| POCO X8 Pro / POCO X8 Pro Max «сильно желтит экран» | Найти замер точки белого (Notebookcheck и т. п.) или ≥ 2 обзора/массовые жалобы. Подтвердилось — `yellow_tint` `verified`. Нет — удалить запись `user_hypothesis` и написать в отчёте пачки «не подтвердилось» |
| Google Pixel «сильно перегреваются» | Проверить КАЖДУЮ модель Pixel (Tensor G2…G5): замер температуры корпуса / стабильность стресс-теста или ≥ 2 источника. Подтверждать по модели, не по бренду |
| Samsung «хороший внутренний AI-ассистент» | Для каждой модели Samsung 2024+: перечень функций Galaxy AI у производителя + ≥ 1 обзор. В `note_ru` — 2–4 функции и что из них работает в РФ. Если в РФ ограничено — добавить `ai_limited_ru` |

**Цель:** хотя бы одна подтверждённая особенность у ≥ 80% моделей. Нашёл особенность, которой нет в справочнике, —
предложи новый тип в отчёте пачки, но в файл не добавляй.

## 10. Источники данных — откуда брать каждое поле

Общие правила:
- **Порядок доверия:** производитель → лаборатория с замерами → база характеристик → обзоры → сообщество.
- **Перекрёстная проверка:** числа, которые различаются между источниками, сверяй минимум по двум. Разошлись —
  бери производителя и пиши `estimated` с обоими источниками.
- **Справочник:** полный список id источников — приложение G.

### 10.1. Фото: правила

1. **Wikimedia Commons** — в первую очередь, лицензии CC0 / CC BY / CC BY-SA. Поиск через API:
   `https://commons.wikimedia.org/w/api.php?action=query&generator=search&gsrnamespace=6&gsrsearch=<модель>&prop=imageinfo&iiprop=url|size|extmetadata&iiurlwidth=960&format=json`.
   Из ответа взять:
   - `url` — превью шириной 960 px (`thumburl`) или оригинал;
   - `author` — из `extmetadata.Artist`, без HTML;
   - `license` — из `LicenseShortName`;
   - `source_page` — страница файла.
2. **Пресс-киты и newsroom производителя** — `license: "press"`, `author` = бренд, `source_page` = страница пресс-кита.
3. **Официальная страница товара** — только если пунктов 1–2 нет; `license: "press"`, `origin: "manufacturer"`.
4. **Нельзя:**
   - картинки GSMArena (защищены и запрещают хотлинк);
   - фото продавцов маркетплейсов;
   - стоковые фото;
   - сгенерированные изображения;
   - фото другой модели или другого цвета «похожего» телефона.
5. **Требования к ссылке:**
   - на фото та самая модель;
   - ширина ≥ 600 px;
   - отдаёт HTTP 200 и `image/*`;
   - протокол только `https://`.
6. **Порядок и состав:** 3–8 фото — спереди, сзади, сбоку или под углом, остальные цвета (`color_ru`). У складных — одно
   фото в раскрытом виде (`kind: "open"`).
7. **Заглушки** (`origin: "placeholder"`, ссылки вида `/placeholder/<slug>/1.svg`) — из рандом-версии. Заменяй их
   настоящими фото и удаляй.

## 14. Частые ошибки — как НЕ надо

| ❌ Неправильно | ✅ Правильно |
|---|---|
| Одна модель для Exynos- и Snapdragon-версии с разными характеристиками | Разные модели, если отличаются чип/камера/батарея; если только регион — одна модель + `aliases` |
| Pro, Pro Max, Ultra перепутаны или слиты | Каждая — отдельный файл; проверяй экран и камеры по официальной странице |
| Redmi K80 Pro и POCO F7 Ultra — один файл | Разные рынки → разные модели; связь только через `aliases`, если характеристики полностью совпадают |
| 4G- и 5G-версия — одна модель | Разные модели («Redmi Note 13» и «Redmi Note 13 5G» — разные чипы) |
| `ram_gb: 24` для «12 ГБ + 12 ГБ виртуальной» | `ram_gb: 12` |
| `rom_gb: 1000` | `rom_gb: 1024` |
| «100× зум» записан как оптический | `max_digital_zoom_x: 100`, оптика — по телевикам |
| `size_inch: "1/1.3"` записан как реальная диагональ 1/1.3 дюйма | Это оптический формат; реальную диагональ — в `diag_mm`, только если её даёт производитель |
| Реальное фокусное расстояние объектива (6,9 мм) | Эквивалентное (24 мм) |
| Сенсор угадан по мегапикселям («50 МП — значит IMX890») | `sensor: null`, пока нет прямого источника |
| ОЗУ iPhone «из головы» | Apple ОЗУ не публикует: бери разбор/Geekbench, `_q: "estimated"` + источник |
| Цена с пошлиной в одной конфигурации и без пошлины в другой | Один принцип для всех конфигураций модели, укажи его в `_src` |
| Отрицательный «прикол» по одному комментарию | Замер или ≥ 2 независимых источника |
| «Прикол» серии перенесён на всю линейку | Проверка каждой модели |
| Процессинг «по бренду» («Google — значит 95») | По обзорам этой модели и этого модуля |
| Фото «похожего» телефона или рендер чужого цвета | Только эта модель, цвет подписан в `color_ru` |
| Пустые строки `""` вместо `null` | `null` |
| Добавлено поле «на всякий случай» | Только поля схемы; идею — в отчёт пачки |
| У старого случайного числа сменили `_q` с `random` на `verified` | Новое значение из источника + ссылка на страницу; не нашёл — оставь `random` и напиши в отчёте |
| `_src: ["gsmarena"]` при `verified` | `_src: ["gsmarena:poco_x8_pro-14001"]` — конкретная страница |
| `quirks_checked: true`, а «приколы» без ссылок | Сначала проверка и ссылки, неподтверждённое — удалить |
| `msrp_usd` = цена в рублях ÷ курс | Официальная цена производителя или `null` |
| `release_date: "2024-06-01"`, потому что «где-то летом» | `"2024-06"` при известном месяце, иначе `null` |

      H1–H11 и R1 раздела 0.1. Доступа нет — пройди таблицу раздела 0.1 вручную по каждому файлу.
- [ ] Каждое изменённое значение — новое, из источника, со ссылкой на страницу. Ни у одного старого числа не сменена
      только пометка `_q`. Что не нашёл — осталось `random` и перечислено в отчёте.
- [ ] У каждого блока есть `_q` и `_src`, id источников есть в `sources.json`; у `verified` — ссылка на страницу.
- [ ] Все официальные конфигурации на месте; ровно одна `is_base: true`; у продающихся в РФ есть цена и дата.
- [ ] Ровно одна камера `main`; у каждой задней камеры заполнены `focal_mm`, `aperture` или стоит `null` с `_q`
      не выше `estimated`; `sensor` — только из справочника или `null`.
- [ ] `processing_score` есть у всех модулей, кроме `depth`; основание — `reviews_rubric` или `dxomark`.
- [ ] `macro_mode`, `max_digital_zoom_x`, `lossless_zoom_x` проверены по производителю.
- [ ] Отрицательные «приколы» — с замером или ≥ 2 ссылками; гипотезы пользователя проверены и сняты или подтверждены;
      `quirks_checked: true`.
- [ ] Категории раздела 9 проставлены; модели вне РФ — `not_sold` и `in_ml: false`.
- [ ] 3–8 фото с лицензией, автором и страницей источника; заглушки удалены; ссылки открываются.
- [ ] Новые чипы, сенсоры и бренды добавлены в справочники в этой же пачке.
- [ ] В отчёте пачки честно перечислено, чего не нашлось.

## 16. Критерии готовности всей работы

| Критерий | Порог |
|---|---|
| Моделей в каталоге | ≥ 950 (цель ≈ 1000) |
| Модели с `_q: "random"` где-либо | 0 |
| Конфигурация `is_base` | у 100% моделей |
| Цена в РФ у базовой конфигурации | у 100% моделей с `availability_ru` ≠ `not_sold` |
| Основная камера с `focal_mm` и `aperture` | ≥ 95% |
| Сенсор основной камеры известен | ≥ 70% |
| `processing_score` у модулей (кроме `depth`) | 100% |
| ≥ 3 настоящих фото / ≥ 1 фото | ≥ 90% / 100% |
| ≥ 1 подтверждённый «прикол» | ≥ 80% моделей; `quirks_checked` у 100% |
| Все модели раздела 9 в базе | 100% |
| `python tools/build_catalog.py --check --final` | 0 ошибок: нет нарушений H1–H11 и R1, все критерии этой таблицы ✓ |
| `cargo test --release` в `rust_backend` | зелёный |

Промежуточные пачки проверяются без `--final`: там допустимо оставшееся `random`, но не нарушения раздела 0.1.

## Приложение C. `schema/catalog_v2.sql` — структура SQLite

```sql
-- Каталог смартфонов, схема v2 (SQLite). Собирается скриптом tools/build_catalog.py из data/catalog/**.json.
-- Источник правды — JSON-файлы; эту БД руками не правят, она пересобирается целиком.
-- q (достоверность): verified | estimated | user_hypothesis | random | unknown.
PRAGMA foreign_keys = ON;

CREATE TABLE meta (
    key   TEXT PRIMARY KEY,           -- schema_version, dataset_name, built_at, files_hash, random_seed
    value TEXT NOT NULL
);

CREATE TABLE sources (
    id          TEXT PRIMARY KEY,     -- 'gsmarena', 'dxomark', 'yandex_market', 'random' …
    name        TEXT NOT NULL,
    url         TEXT,
    kind        TEXT NOT NULL CHECK (kind IN ('manufacturer','press','spec_db','wiki','lab','review','community',
                                              'retailer','project','user','random')),
    reliability INTEGER NOT NULL CHECK (reliability BETWEEN 0 AND 5)
);

CREATE TABLE brands (
    id      INTEGER PRIMARY KEY,
    slug    TEXT NOT NULL UNIQUE,
    name    TEXT NOT NULL,
    parent  TEXT,                     -- slug материнского бренда (poco → xiaomi)
    country TEXT
);

CREATE TABLE chipsets (
    id           INTEGER PRIMARY KEY,
    slug         TEXT NOT NULL UNIQUE,
    name         TEXT NOT NULL,
    vendor       TEXT NOT NULL,
    process_nm   REAL,
    antutu_k     INTEGER,
    geekbench_sc INTEGER,
    geekbench_mc INTEGER,
    year         INTEGER,
    q            TEXT NOT NULL,
    src          TEXT                 -- JSON-массив id источников
);

CREATE TABLE phones (
    id              INTEGER PRIMARY KEY,      -- внутренний номер, меняется при пересборке — снаружи используйте slug
    slug            TEXT NOT NULL UNIQUE,
    brand_id        INTEGER NOT NULL REFERENCES brands(id),
    name            TEXT NOT NULL,
    full_name       TEXT NOT NULL,
    aliases         TEXT,                     -- JSON-массив
    os              TEXT NOT NULL CHECK (os IN ('Android','iOS','HarmonyOS')),
    release_date    TEXT,
    year            INTEGER NOT NULL,
    status          TEXT NOT NULL CHECK (status IN ('on_sale','discontinued','announced','china_only')),
    availability_ru TEXT NOT NULL CHECK (availability_ru IN ('official','parallel_import','not_sold')),
    form_factor     TEXT NOT NULL CHECK (form_factor IN ('bar','book_fold','flip','trifold','rugged','other')),
    in_ml           INTEGER NOT NULL DEFAULT 1,
    chipset_id      INTEGER REFERENCES chipsets(id),
    screen_in       REAL NOT NULL,
    cover_screen_in REAL,
    refresh_hz      INTEGER NOT NULL,
    display_type    TEXT,
    peak_nits       INTEGER,
    battery_mah     INTEGER NOT NULL,
    charge_w        REAL NOT NULL,
    wireless_w      REAL,
    weight_g        REAL NOT NULL,
    thickness_mm    REAL,
    ip_rating       TEXT,
    has_5g          INTEGER NOT NULL,

-- Совместимость с текущим ML (18 признаков, одна строка на модель — базовая конфигурация).
-- active_h / standby_d остаются расчётными (формула estimate_autonomy в src/db.py) и считаются в Python.
CREATE VIEW v_ml_phones AS
SELECT p.id, p.slug, b.name AS brand, p.name AS model, p.full_name, p.os, p.year,
       v.price_rub, v.ram_gb, v.rom_gb, p.battery_mah, p.screen_in, p.refresh_hz, p.weight_g,
       (SELECT c.mp FROM phone_cameras c WHERE c.phone_id = p.id AND c.role = 'main' ORDER BY c.position LIMIT 1) AS camera_mp,
       ch.antutu_k, p.charge_w, p.has_5g, p.nfc, p.esim, p.ir_port
FROM phones p
JOIN brands b ON b.id = p.brand_id
JOIN variants v ON v.phone_id = p.id AND v.is_base = 1
LEFT JOIN chipsets ch ON ch.id = p.chipset_id
WHERE p.in_ml = 1;

-- Лёгкая карточка для ленты: «от N ₽», число конфигураций, сводка камер
CREATE VIEW v_phone_card AS
SELECT p.id, p.slug, p.full_name, p.os, p.year, p.form_factor,
       (SELECT MIN(price_rub) FROM variants v WHERE v.phone_id = p.id) AS price_from,
       (SELECT COUNT(*) FROM variants v WHERE v.phone_id = p.id) AS variants_count,
       (SELECT MAX(ram_gb) FROM variants v WHERE v.phone_id = p.id) AS ram_max,
       s.rear_count, s.max_optical_zoom_x, s.max_digital_zoom_x, s.macro_mode, s.overall_score,
       (SELECT url FROM photos ph WHERE ph.phone_id = p.id ORDER BY position LIMIT 1) AS photo
FROM phones p
LEFT JOIN camera_summary s ON s.phone_id = p.id;
```
